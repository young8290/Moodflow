# 0007 Hub 核心与外壳分离，在 Moodflow fork 建好前先在本仓库开发
- 状态：提议
- 日期：2026-10-04；决策人：待 W1 评审确认

## 背景
14 第 1 节规划代码放在 Moodflow 的私有 fork 中，Hub 后端位于 `moodflow_hub/src-tauri/`，领域层与 Tauri 命令在同一个 crate。
目前 fork 尚未建立；同时 Tauri 依赖 WebView，在 Linux CI 上测试领域逻辑需要额外的系统库，而 NFR-MNT-03 本来就要求领域层不得依赖 tauri / windows。

## 决策
1. 把与平台无关的部分拆成独立 crate：
   - `crates/mfp`：MFP 消息类型与帧编解码（核心 tap crate、Hub、mf-sim 共用，契约仍以 `protocol/mfp.schema.json` 为准）；
   - `moodflow_hub/core`（crate 名 `moodflow-hub-core`）：17 第 2.1 节中的 `domain/`，以及不依赖 Windows 的基础层（store、gateway 的 trait/熔断/预算/脱敏、clock、templates）；
   - `moodflow_hub/gateway`（crate 名 `moodflow-hub-gateway`）：AI 网关的 HTTP 实现（JevClient、LlmClient），依赖 reqwest。单独成 crate 是为了让 core 不依赖 reqwest（TC-AIG-06）；
   - 数据库迁移脚本放在 `moodflow_hub/core/migrations/`（09 第 3 节原定 `src-tauri/migrations/`）。
2. `moodflow_hub/src-tauri/` 落地时只放 Tauri 外壳、命令层和 Windows 专属基础设施（命名管道客户端、DPAPI、Toast、单实例），依赖 `moodflow-hub-core`。
3. fork 建好之前，以上代码和 `tools/` 都在本仓库（young8290/xinqing）开发，根目录是一个 Cargo workspace；建 fork 时按 14 第 1 节第 6 步整体复制过去，`crates/mfp` 同时供 `moodflow-tap` 引用。

## 备选方案与取舍
- 全部放进 `src-tauri`：与 17 字面一致，但 Linux CI 需要安装 WebKitGTK 才能编译测试，且分层只能靠约定保证。
- 等 fork 建好再开工：A-01 在关键路径上，B、C、D 会被阻塞（16 第 4 节）。

## 影响
- 17 第 2.1 节目录结构：`domain/` 与部分 `infra/` 实际位于 `moodflow_hub/core/src/`；`infra/gateway/` 里的 JevClient、LlmClient 实际在 `moodflow_hub/gateway/`；
- 09 第 3 节“迁移脚本位置”；14 第 6 节 CI 增加 Linux 上的 Rust 检查和 Windows 上的编译测试。
- 10 第 6.2 节“完整清单以 `src-tauri/src/settings/keys.rs` 为准”：设置键注册表实际在 `moodflow_hub/core/src/domain/settings.rs` 的 `KEYS`；
- 外壳落地后 workspace 包含 `moodflow_hub/src-tauri`，Linux CI 为编译它安装 WebKitGTK；领域层仍可单独 `cargo test -p moodflow-hub-core`，不受影响。
- 接受后同步修改 17、09、14 并在 00 第 5 节记录。
